\noindent\textbf{Overview.} The Librarian is a retrieval-augmented question answering service over the Streamlit
documentation, its closed GitHub issues and its release notes (404 pages, 418 issues, 60 releases $\rightarrow$ 3{,}562
indexed chunks); it answers only from retrieved passages, cites the source behind every claim with \texttt{[n]} markers, and
replies ``I don't know'' when the passages do not contain the answer. On our 112-question evaluation it answers correctly
\textbf{89.7\%} of the time with \textbf{98.3\%} of claims supported by a retrieved passage, at \textbf{\$0.00057} and
\textbf{1.2\,s} per question.

\section{Architecture and model choices}

\textit{Offline (run once):} \texttt{build\_corpus.py} clones the docs and pulls issues and releases through the GitHub API,
stripping personal data; \texttt{index\_corpus.py} cleans and chunks the text ($\approx$250 words, code blocks never split),
gives each chunk a dense meaning vector and a sparse BM25 vector, and upserts it into Qdrant.
\textit{Online (per question):} the question (optionally rewritten by the model) goes to keyword search and vector search
(50 candidates each); the two lists are fused by reciprocal rank fusion; an optional filter keeps only docs, issues or
releases; the top \textbf{10} chunks go to the generator, which answers with \texttt{[n]} citations or ``I don't know''.
A FastAPI service and web page wrap this and log cost and latency; rate limits cap each visitor at 10 questions/minute and
the service at 300/day.

Embedding model & \texttt{BAAI/\allowbreak bge-small-\allowbreak en-v1.5} (384-dim, ONNX/fastembed) &
Strong retrieval quality for its size on the MTEB benchmark while only 384 dimensions, so storage and search stay cheap.
It runs on CPU with no GPU and no embedding API, which keeps the service free and under the 512\,MB host limit. \\
\addlinespace
Vector database & Qdrant Cloud (one collection, named \texttt{dense} + \texttt{bm25} vectors) &
Stores both vectors per point and computes the BM25 word-rarity (IDF) weights server-side, so hybrid search is a single
query. Point ids are derived from the document id and chunk number, so adding or replacing a document is one upsert with no
rebuild --- unlike our first flat-file index, which had to be rebuilt for every new document. Free tier keeps the app small. \\
\addlinespace
Generative model & \texttt{gpt-4o-mini}, temperature 0 &
Follows the strict contract (cite every factual sentence; use nothing outside the passages; reply exactly ``I don't know'')
reliably at \$0.15/\$0.60 per million input/output tokens. Retrieval, not the generator, is the accuracy ceiling
(faithfulness is already 98\%+), so a larger model buys little; \texttt{gpt-4.1-mini}/\texttt{nano} were available but did not
justify the change. \\
\addlinespace
Grader (judge) model & \texttt{gpt-4.1-mini}, temperature 0, JSON mode &
A different and stronger family than the generator, which avoids self-preference bias when an LLM scores LLM answers.
Re-grading the baseline moved accuracy only 86.2\%$\rightarrow$85.3\%, confirming the headline is not inflated by a model
grading its own family. It runs only during evaluation ($\approx$\$0.17 per 112-question run), never in the live service. \\

\end{tabular}

\section{Optimization}

Almost all per-question cost (85\%) is input tokens, and almost all of the input is the passages; search itself is free
(embeddings run locally, Qdrant is on a free tier). We measured both directions on the same 112 questions under the
independent grader. \textbf{Accuracy:} sending 10 passages instead of 5 puts the gold passage in front of the model 87\% of
the time instead of 77\% and raises accuracy \textbf{+4.4 points} at no latency cost and about \$0.00025 more per question ---
this is the \textbf{deployed} configuration. A cross-encoder reranker (top 30 $\rightarrow$ best 5) lifts recall but
\textit{lowers} end-to-end accuracy 1.8 points and triples latency on a CPU, so it is not used.

\noindent\textbf{Cost (Week 8 target).} The brief asked to cut cost or p95 latency by 50\% within a 2-point accuracy loss.
Sending only 2 passages cuts cost 53\% (\$0.00015) but, measured on the same set, drops accuracy about 9 points --- well past
the budget --- so we did not adopt it. Two savings cost nothing: we skip the reranker ($\approx$3.5\,s/question avoided), and
the service answers repeated questions from an in-memory cache with no search and no model call. Full before/after numbers
are in \texttt{optimisation.md}.

\section{Evaluation}

Retrieval and generation are measured separately. The set is 100 answerable questions (each with a reference answer and one
or more exact source passages) and 12 unanswerable questions about features Streamlit does not have. A question counts as
``found at $k$'' if any of the top $k$ chunks contains one of its passages; the scripts recompute this for whichever
collection they test.

\noindent\textbf{Retrieval ablation.} Fusing keyword and vector search beats either alone; the reranker helps the top ranks
but is too slow for an interactive service (times include the round trip to Qdrant Cloud).

\noindent\textbf{Reading the numbers.} When the right passage reaches the model it rarely strays beyond it (98.3\%
faithfulness, 98.8\% citation accuracy); the remaining errors are mostly retrieval misses --- the gold passage was among the
10 sent for 87\% of questions, and most not-fully-correct answers never received it. ``I don't know'' works in both
directions: 100\% on unanswerable questions, 4\% on answerable ones. Better retrieval would raise accuracy more than a better
prompt. A full postmortem of 23 problems and fixes is in \texttt{postmortem.md}.
